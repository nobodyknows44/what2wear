# bankrot-radar

Сбор, нормализация, оценка и скоринг лотов торгов по банкротству (127-ФЗ) и имущественных торгов.

Сервис отвечает на один вопрос: **какие из трёх тысяч сегодняшних лотов стоят вашего внимания
в ближайший час**. Он не покупает, не подаёт заявки и не подписывает ничего вашей ЭЦП — эти
границы проведены сознательно, обоснование в [docs/strategy.md](docs/strategy.md).

## Что он делает

```
источники → нормализация → дедупликация → оценка → скоринг → алерт
```

- **Собирает** лоты из ЕФРСБ (первоисточник по 127-ФЗ) и ГИС Торги (арестованное и гос/мун имущество).
- **Нормализует**: вытаскивает из текста извещения кадастровый номер, VIN, площадь, ИНН должника,
  номер дела, размер задатка и формулу снижения цены.
- **Дедуплицирует**: один объект из разных источников — одна запись, поля сливаются, а не затираются.
- **Разворачивает график цены**: «снижение каждые 7 дней на 10% до 50%» превращается в таблицу
  периодов, по которой считается текущая цена и момент следующего снижения.
- **Оценивает** по собственной накопленной базе состоявшихся продаж.
- **Скорит** с учётом дисконта, ликвидности, срочности и риск-флагов — и объясняет каждый балл.
- **Шлёт алерты** в Telegram, без повторов по одному и тому же лоту.

## Быстрый старт

Нужен только Node 22.18+. Ни базы, ни ключей, ни нативных зависимостей.

```bash
npm install          # только devDependencies: typescript и @types/node
npm run demo         # заливает демо-данные и прогоняет весь конвейер офлайн
npm test             # 95 тестов
```

`npm run demo` покажет ранжированные лоты с объяснением каждого балла. Данные синтетические,
но проходят через тот же нормализатор, ту же оценку и тот же скоринг, что и боевые.

## Боевой запуск

```bash
cp .env.example .env    # заполнить ключи и фильтры
npm run ingest          # собрать лоты
npm run score           # пересчитать оценку и баллы
npm run alert           # разослать уведомления
npm run radar -- top    # посмотреть топ в терминале
npm run radar -- stats  # состояние базы, наполненность выборки, журнал прогонов
```

Фазы разделены намеренно: сбор имеет смысл гонять чаще, чем скоринг, а алерты — держать
выключенными, пока подбираются пороги, не прерывая накопление данных.

```cron
*/15 * * * *  cd /opt/bankrot-radar && npm run ingest
0    * * * *  cd /opt/bankrot-radar && npm run score
5    * * * *  cd /opt/bankrot-radar && npm run alert
0    4 * * 0  cd /opt/bankrot-radar && npm run radar -- harvest --days 180
```

## Наполнение базы аналогов

Оценка строится на собственной истории состоявшихся продаж, поэтому первым делом её надо
наполнить. Пока таблица пуста, оценки нет, и скоринг честно ограничивает такие лоты 45 баллами.

Два пути, они дополняют друг друга:

```bash
# 1. Из ЕФРСБ — основной путь, нужен ключ.
#    Окно широкое: сообщение о результатах публикуется через месяцы после торгов.
npm run radar -- harvest --days 180

# 2. Из CSV — чтобы завести базу уже сегодня, из выгрузки агрегатора или своей таблицы.
npm run radar -- import-sales sales.csv
```

CSV понимает и русские, и английские заголовки, точку с запятой как разделитель, числа вида
`1 200 000,50` и даты `15.05.2026`. Минимально нужна колонка с ценой продажи; чем больше
остальных (начальная цена, регион, площадь, дата), тем полезнее запись:

```csv
Наименование;Регион;Площадь;Начальная цена;Цена продажи;Дата
Квартира 48 кв.м, Москва;77;48;11000000;9100000;15.05.2026
```

Записи без начальной цены или с неопознанным видом имущества отбрасываются — отчёт об импорте
показывает, сколько и почему. Записи с отношением цены продажи к начальной выше двадцатикратного
тоже отбрасываются: это перепутанные колонки или лишние нули, и одна такая строка перекашивает
медиану по всей категории.

Результаты торгов из ЕФРСБ приходят без характеристик объекта — они были в объявлении,
опубликованном месяцами раньше. Недостающие поля добираются из уже известного лота по тому же
ключу дедупликации, каким склеиваются лоты между источниками. Связка надёжна, когда в тексте
есть кадастровый номер или VIN.

`npm run radar -- stats` показывает наполненность по видам имущества и сколько записей
не хватает до порога, на котором оценка начнёт работать.

## Источники

| Источник | Что даёт | Доступ | Статус |
|---|---|---|---|
| **ЕФРСБ / Федресурс** | Первоисточник по 127-ФЗ: все сообщения о торгах и **результаты состоявшихся торгов** | REST API по договору, есть бесплатный лимит | выключен по умолчанию, нужен ключ |
| **ГИС Торги** | Гос/мун имущество, аренда, арестованное имущество. Банкротства здесь нет | Открытый JSON, без авторизации | включён |
| Коммерческий агрегатор | Нормализованные лоты со 100+ ЭТП | По подписке, API есть не у всех | не подключён, см. ниже |

### Про ЕФРСБ

Имена полей и пути методов различаются между версиями спецификации REST API, поэтому транспорт
полностью параметризуется через окружение (`FEDRESURS_SEARCH_PATH`, `FEDRESURS_AUTH_HEADER`),
а маппер читает каждое поле по списку допустимых имён:

```ts
readString(item, 'startPrice', 'priceStart', 'beginPrice', 'price')
```

Перед первым боевым прогоном сверьте имена с вашей версией спецификации и допишите фактические
первыми в списки в `src/normalize/fromFedresurs.ts` — остальное продолжит работать. Фикстуры
в тестах синтетические: они проверяют логику маппера, а не соответствие реальной схеме.

### Про агрегатор

Подключать коммерческий агрегатор имеет смысл только при наличии у него API или регулярной
выгрузки. Новый источник — это один класс, реализующий `Source`, плюс маппер в `src/normalize/`.
Всё остальное (дедупликация, оценка, скоринг, алерты) переиспользуется как есть.

## Конфигурация

Все параметры — через окружение, см. `.env.example`. Ключевые:

| Переменная | Смысл |
|---|---|
| `FILTER_REGIONS` | Коды регионов воронки: `77,50,78`. Пусто — вся страна |
| `FILTER_ASSET_KINDS` | `real_estate,land,vehicle,equipment,claim,share,other` |
| `ALERT_MIN_SCORE` | Порог балла для уведомления, по умолчанию 65 |
| `ESTIMATE_MIN_COMPARABLES` | Минимум сопоставимых продаж, ниже которого оценка не выдаётся |
| `ESTIMATE_UPLIFT` | Множитель к медиане цен реализации. 1.0 = «за сколько лот реально уходит с торгов» |

## Как устроен скоринг

```
балл = 0.55 × дисконт + 0.30 × ликвидность + 0.15 × срочность − штраф за риски
```

- **Дисконт** считается к оценке; 60% дисконта дают максимум по этому компоненту.
- **Ликвидность** — экспертная таблица по виду имущества с поправкой на регион. Заменяется
  на статистику, как только накопятся собственные сделки.
- **Срочность** учитывает, что на подготовку пакета и перевод задатка нужны дни, а не часы.
- **Штраф за риски** растёт нелинейно: один тяжёлый флаг весит больше трёх мелких.

Два поведения заданы намеренно:

- **Лот без оценки не может получить больше 45 баллов.** Без базы сравнения высокий балл не заслужен.
- **После окончания приёма заявок балл обнуляется.** Лот, куда уже нельзя подать заявку,
  не должен всплывать в топе, каким бы дешёвым он ни выглядел.

Каждый балл сопровождается списком причин — они же уходят в текст алерта.

## Риск-флаги

Разбор текста извещения ищет то, что теряет деньги чаще, чем неверная оценка цены: действующую
аренду, зарегистрированных жильцов, долю в праве, незарегистрированное право собственности,
судебный спор, признаки единственного жилья, самострой, отсутствие документов, запрет осмотра.
Каждый флаг сопровождается цитатой из текста, чтобы его можно было проверить, а не принимать на веру.

Это сортировщик внимания, а не юридическая проверка.

## Архитектура

```
src/
  domain/       модель лота, график цены, дедупликация, регионы
  normalize/    извлечение из текста, сборка лота, мапперы источников
  sources/      HTTP-клиент, ЕФРСБ, ГИС Торги
  import/       импорт результатов торгов из CSV
  enrich/       оценка по сопоставимым продажам, разрешение записей о продажах
  score/        риск-флаги, ликвидность, сводный балл
  storage/      SQLite: лоты, история цен, баллы, продажи, алерты, прогоны
  notify/       формат сообщения, Telegram и консоль
  pipeline.ts   ingest / harvest / score / alert
  cli.ts        точка входа
```

Зависимостей в рантайме нет: HTTP — встроенный `fetch`, база — встроенный `node:sqlite`,
TypeScript исполняется Node напрямую. Сервис, который годами крутится по cron, не должен падать
из-за пересборки нативного модуля.

Схема БД совместима с Postgres по структуре — миграция сводится к замене драйвера в `storage/db.ts`.

## Что дальше

По убыванию отдачи:

1. **Обогащение**: ЕГРН по кадастровому номеру, реестр залогов ФНП по VIN, карточка дела в КАД.
2. **LLM поверх остатка.** Детерминированные правила покрывают типовые формулировки; языковая
   модель имеет смысл на том, что они не разобрали, — и результат нужно складывать в те же поля,
   чтобы оставалась воспроизводимость.
3. **Чек-лист подачи**: комплект документов, расчёт задатка, напоминания по дедлайнам.
4. **Учёт сделок**: воронка от интереса до перепродажи, чтобы ликвидность считалась по факту,
   а не по экспертной таблице.
5. **Замена экспертной таблицы ликвидности** в `src/score/liquidity.ts` на статистику из
   накопленных сделок: медианный срок от покупки до перепродажи по своим же операциям.

Чего здесь сознательно нет — подачи заявок и автоматических ценовых предложений. Причины
в [docs/strategy.md](docs/strategy.md): ключ УКЭП нельзя передавать сервису, а роботы-снайперы
дешевле арендовать готовыми, чем писать и сопровождать.

## Вынести в отдельный репозиторий

Проект самодостаточен и не связан с кодом вокруг. Перенос с сохранением истории:

```bash
git subtree split --prefix=bankrot-radar -b bankrot-radar-only
git push git@github.com:<owner>/bankrot-radar.git bankrot-radar-only:main
```

Либо просто скопировать каталог — внешних ссылок за его пределы нет.
