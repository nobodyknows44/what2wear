# bankrot-radar

Сбор, нормализация, оценка и скоринг лотов торгов по банкротству (127-ФЗ) и имущественных торгов.

Сервис отвечает на один вопрос: **какие из трёх тысяч сегодняшних лотов стоят вашего внимания
в ближайший час**. Он не покупает, не подаёт заявки и не подписывает ничего вашей ЭЦП — эти
границы проведены сознательно, обоснование в [docs/strategy.md](docs/strategy.md).

## Что он делает

```
источники → нормализация → дедупликация → оценка → скоринг ─┬─→ алерт
                                                            └─→ обогащение реестрами
                                                                  (только кандидаты) ──┘
```

- **Собирает** лоты из ЕФРСБ (первоисточник по 127-ФЗ) и ГИС Торги (арестованное и гос/мун имущество).
- **Нормализует**: вытаскивает из текста извещения кадастровый номер, VIN, площадь, ИНН должника,
  номер дела, размер задатка и формулу снижения цены.
- **Дедуплицирует**: один объект из разных источников — одна запись, поля сливаются, а не затираются.
  Там, где устойчивого идентификатора нет, склейка между источниками сознательно не делается:
  дубль в воронке дешевле потерянного лота.
- **Разворачивает график цены**: «снижение каждые 7 дней на 10% до 50%» превращается в таблицу
  периодов, по которой считается текущая цена и момент следующего снижения.
- **Оценивает** по собственной накопленной базе состоявшихся продаж.
- **Скорит** с учётом дисконта, ликвидности, срочности и риск-флагов — и объясняет каждый балл.
- **Обогащает кандидатов** данными реестров: факт из ЕГРН весит больше догадки по тексту,
  а подтверждённое «обременений нет» её отменяет.
- **Ведёт сделку**: статусы от интереса до регистрации права, сроки назад от окончания
  приёма заявок в рабочих днях, пакет документов по типу покупателя.
- **Шлёт алерты и напоминания** в Telegram, без повторов по одному и тому же лоту.

## Быстрый старт

Нужен только Node 22.18+. Ни базы, ни ключей, ни нативных зависимостей.

```bash
npm install          # только devDependencies: typescript и @types/node
npm run demo         # заливает демо-данные и прогоняет весь конвейер офлайн
npm test             # 180 тестов
```

`npm run demo` покажет ранжированные лоты с объяснением каждого балла. Данные синтетические,
но проходят через тот же нормализатор, ту же оценку и тот же скоринг, что и боевые.

## Боевой запуск

```bash
cp .env.example .env    # заполнить ключи и фильтры
npm run ingest          # собрать лоты
npm run score           # пересчитать оценку и баллы
npm run alert           # разослать уведомления
npm run radar -- top    # посмотреть топ в терминале
npm run radar -- stats  # состояние базы, наполненность выборки, журнал прогонов
npm run radar -- doctor # полнота извлечения: что именно не разбирается и на каких лотах
npm run radar -- backtest # проверка оценки на собственной истории продаж
```

Фазы разделены намеренно: сбор имеет смысл гонять чаще, чем скоринг, а алерты — держать
выключенными, пока подбираются пороги, не прерывая накопление данных.

Для регулярной работы фазы не расписываются по отдельности — см. «Развёртывание».

## Развёртывание

```bash
cp .env.example .env          # заполнить
docker compose up -d scheduler        # регулярный прогон
docker compose run --rm radar doctor  # разовые команды
```

Либо без Docker, на голой машине:

```bash
crontab deploy/crontab        # предварительно поправив RADAR_DIR
```

**Одна команда вместо пяти.** `deploy/run-cycle.sh` прогоняет сбор → скоринг → обогащение →
алерты → напоминания по порядку. Пять независимых записей в cron рано или поздно разъедутся,
и сервис начнёт слать алерты по вчерашним баллам.

**Блокировка обязательна.** Сбор при широком окне идёт дольше пятнадцати минут, и без `flock`
прогоны наложатся, удвоив нагрузку на источники — ровно то, за что площадки блокируют доступ.
Занятый замок означает пропуск прогона, а не ошибку.

**Падение одной фазы не отменяет остальные.** Если ЕФРСБ лежит, скоринг по уже собранным
лотам и напоминания по срокам всё равно нужны. Скрипт сообщает, какие фазы упали, и
возвращает ненулевой код только тогда, когда упала хоть одна.

**Ненастроенный провайдер — не ошибка.** Выключенный источник или отсутствие ключей
к реестрам дают предупреждение и нулевой код: иначе регулярный прогон вечно рапортовал бы
о сбое и приучил не читать свой лог.

База лежит в томе `/data`. Контейнер пересоздаётся при обновлении, а накопленная история
продаж и кэш реестров — самое ценное, что есть у сервиса, и переживать обновление обязаны.
Часовой пояс контейнера — Москва, чтобы логи читались без пересчёта в уме.

## Наполнение базы аналогов

Оценка строится на собственной истории состоявшихся продаж, поэтому первым делом её надо
наполнить. Пока таблица пуста, оценки нет, и скоринг честно ограничивает такие лоты 45 баллами.

Два пути, они дополняют друг друга:

```bash
# 1. Из ЕФРСБ — основной путь, нужен ключ.
#    Окно широкое: сообщение о результатах публикуется через месяцы после торгов.
npm run radar -- harvest --days 180

# 2. Из CSV — чтобы завести базу уже сегодня, из выгрузки агрегатора или своей таблицы.
npm run radar -- import-sales sales.csv
```

CSV понимает и русские, и английские заголовки, точку с запятой как разделитель, числа вида
`1 200 000,50` и даты `15.05.2026`. Минимально нужна колонка с ценой продажи; чем больше
остальных (начальная цена, регион, площадь, дата), тем полезнее запись:

```csv
Наименование;Регион;Площадь;Начальная цена;Цена продажи;Дата
Квартира 48 кв.м, Москва;77;48;11000000;9100000;15.05.2026
```

Записи без начальной цены или с неопознанным видом имущества отбрасываются — отчёт об импорте
показывает, сколько и почему. Записи с отношением цены продажи к начальной выше двадцатикратного
тоже отбрасываются: это перепутанные колонки или лишние нули, и одна такая строка перекашивает
медиану по всей категории.

Результаты торгов из ЕФРСБ приходят без характеристик объекта — они были в объявлении,
опубликованном месяцами раньше. Недостающие поля добираются из уже известного лота по тому же
ключу дедупликации, каким склеиваются лоты между источниками. Связка надёжна, когда в тексте
есть кадастровый номер или VIN.

`npm run radar -- stats` показывает наполненность по видам имущества и сколько записей
не хватает до порога, на котором оценка начнёт работать.

## Обогащение данными реестров

Риск-флаги по тексту извещения — догадки. Реестр даёт факты. Разница видна в скоринге:
реестровый флаг весит больше текстового, а **реестровое «обременений нет» отменяет
текстовую догадку** — слово «залог» в извещении часто относится к положению должника,
а не к конкретному объекту.

```bash
npm run radar -- enrich            # обогатить кандидатов и пересчитать их балл
npm run radar -- enrich --min 70   # только совсем верхушку
```

Запросы к реестрам платные и лимитированные, поэтому:

- **Обогащаются только кандидаты.** Сначала весь поток ранжируется по тому, что известно
  бесплатно, затем реестры опрашиваются по верхушке. Порог — `ENRICH_MIN_SCORE`.
- **Ответы кэшируются** на 30 дней для ЕГРН и 7 для ФНП. Выписка не меняется день ото дня.
- **Ошибки кэшируются на сутки**, чтобы упавший провайдер не опрашивался на каждом лоте.
- **Бюджет на прогон** (`ENRICH_MAX_REQUESTS`) — страховка от ошибки в логике отбора:
  она не должна оборачиваться тысячей платных запросов.
- Уже оплаченные факты сохраняются и подхватываются обычным `score` — повторно за них
  не платим.

### Начать без API

Официальных открытых API ни у ЕГРН, ни у реестра залогов ФНП нет. Самый быстрый старт —
проверить несколько объектов руками и сложить результат в файл:

```json
{
  "77:06:0004009:1234": [
    { "code": "egrn.area", "value": 54.3, "detail": "выписка ЕГРН от 05.08.2026" },
    { "code": "egrn.encumbrance.none", "value": true }
  ],
  "77:05:0011007:8899": [
    { "code": "egrn.encumbrance.lease", "value": true, "detail": "аренда до 15.03.2028" }
  ]
}
```

```bash
ENRICH_MANUAL_FACTS=./facts.json npm run radar -- enrich
```

Ключ — кадастровый номер, VIN или идентификатор лота. Ручные факты идут первыми и бюджет
не тратят: проверенное человеком достовернее любого автоматического ответа.

### Коды фактов

| Код | Что означает | Во что превращается |
|---|---|---|
| `egrn.area` | Площадь по ЕГРН | Исправляет площадь, вытащенную из текста |
| `egrn.encumbrance.lease` | Зарегистрирована аренда | Флаг `lease`, тяжесть 3 |
| `egrn.encumbrance.mortgage` | Ипотека | Флаг `pledge`, тяжесть 1 |
| `egrn.encumbrance.arrest` | Арест | Флаг `restricted`, тяжесть 3 |
| `egrn.encumbrance.none` | Обременений нет | Снимает текстовые `lease`, `pledge`, `restricted` |
| `egrn.rights.absent` | Право не зарегистрировано | Флаг `unregistered`, тяжесть 3 |
| `egrn.shared_ownership` | Долевая собственность | Флаг `fractional`, тяжесть 3 |
| `fnp.pledge.active` | Действующий залог по VIN | Флаг `pledge`, тяжесть 2 |
| `fnp.pledge.none` | Залога нет | Снимает текстовый `pledge` |

Отсутствие обременений фиксируется, только если провайдер вернул сам список и тот оказался
пустым. Сбой разбора не должен читаться как «объект чистый» — это разные вещи, и вторая
опаснее. По той же причине подтверждённый факт не отменяется другим реестром: залог по ФНП
сильнее, чем «чисто» по ЕГРН, потому что ЕГРН про автомобили ничего не знает.

Исправленная площадь — не косметика: оценка недвижимости считается по цене за метр,
поэтому ошибка в площади на 40% даёт ошибку в оценке на 40%.

Подключение сетевых провайдеров — в `.env.example`. Разбор ответа вынесен в чистые функции
`factsFromEgrnResponse` и `factsFromFnpResponse`: под своего провайдера правятся только они,
кэш, бюджет и скоринг остаются нетронутыми.

## Источники

| Источник | Что даёт | Доступ | Статус |
|---|---|---|---|
| **ЕФРСБ / Федресурс** | Первоисточник по 127-ФЗ: все сообщения о торгах и **результаты состоявшихся торгов** | REST API по договору, есть бесплатный лимит | выключен по умолчанию, нужен ключ |
| **ГИС Торги** | Гос/мун имущество, аренда, арестованное имущество. Банкротства здесь нет | Открытый JSON, без авторизации | включён |
| Коммерческий агрегатор | Нормализованные лоты со 100+ ЭТП | По подписке, API есть не у всех | не подключён, см. ниже |

### Про ЕФРСБ

Имена полей и пути методов различаются между версиями спецификации REST API, поэтому транспорт
полностью параметризуется через окружение (`FEDRESURS_SEARCH_PATH`, `FEDRESURS_AUTH_HEADER`),
а маппер читает каждое поле по списку допустимых имён:

```ts
readString(item, 'startPrice', 'priceStart', 'beginPrice', 'price')
```

Перед первым боевым прогоном сверьте имена с вашей версией спецификации и допишите фактические
первыми в списки в `src/normalize/fromFedresurs.ts` — остальное продолжит работать. Фикстуры
в тестах синтетические: они проверяют логику маппера, а не соответствие реальной схеме.

### Про агрегатор

Подключать коммерческий агрегатор имеет смысл только при наличии у него API или регулярной
выгрузки. Новый источник — это один класс, реализующий `Source`, плюс маппер в `src/normalize/`.
Всё остальное (дедупликация, оценка, скоринг, алерты) переиспользуется как есть.

## Конфигурация

Все параметры — через окружение, см. `.env.example`. Ключевые:

| Переменная | Смысл |
|---|---|
| `FILTER_REGIONS` | Коды регионов воронки: `77,50,78`. Пусто — вся страна |
| `FILTER_ASSET_KINDS` | `real_estate,land,vehicle,equipment,claim,share,other` |
| `ALERT_MIN_SCORE` | Порог балла для уведомления, по умолчанию 65 |
| `ESTIMATE_MIN_COMPARABLES` | Минимум сопоставимых продаж, ниже которого оценка не выдаётся |
| `ESTIMATE_UPLIFT` | Множитель к медиане цен реализации. 1.0 = «за сколько лот реально уходит с торгов» |

## Как устроен скоринг

```
балл = 0.55 × дисконт + 0.30 × ликвидность + 0.15 × срочность − штраф за риски
```

- **Дисконт** считается к оценке; 60% дисконта дают максимум по этому компоненту.
- **Ликвидность** — экспертная таблица по виду имущества с поправкой на регион. Заменяется
  на статистику, как только накопятся собственные сделки.
- **Срочность** учитывает, что на подготовку пакета и перевод задатка нужны дни, а не часы.
- **Штраф за риски** растёт нелинейно: один тяжёлый флаг весит больше трёх мелких.

Два поведения заданы намеренно:

- **Лот без оценки не может получить больше 45 баллов.** Без базы сравнения высокий балл не заслужен.
- **После окончания приёма заявок балл обнуляется.** Лот, куда уже нельзя подать заявку,
  не должен всплывать в топе, каким бы дешёвым он ни выглядел.

Каждый балл сопровождается списком причин — они же уходят в текст алерта.

## Риск-флаги

Разбор текста извещения ищет то, что теряет деньги чаще, чем неверная оценка цены: действующую
аренду, зарегистрированных жильцов, долю в праве, незарегистрированное право собственности,
судебный спор, признаки единственного жилья, самострой, отсутствие документов, запрет осмотра.
Каждый флаг сопровождается цитатой из текста, чтобы его можно было проверить, а не принимать на веру.

Это сортировщик внимания, а не юридическая проверка.

## Архитектура

```
src/
  domain/       модель лота, график цены, дедупликация, регионы
  normalize/    извлечение из текста, сборка лота, мапперы источников
  sources/      HTTP-клиент, ЕФРСБ, ГИС Торги
  import/       импорт результатов торгов из CSV
  deal/         вехи подготовки, чек-лист документов
  diagnostics/  полнота извлечения, проверка оценки на истории
  enrich/       оценка по продажам, обогащение реестрами, кэш и бюджет запросов
  score/        риск-флаги, реестровые факты, ликвидность, сводный балл
  storage/      SQLite: лоты, история цен, баллы, продажи, алерты, прогоны
  notify/       формат сообщения, Telegram и консоль
  pipeline.ts   ingest / harvest / score / enrich / alert / remind
  cli.ts        точка входа
```

Зависимостей в рантайме нет: HTTP — встроенный `fetch`, база — встроенный `node:sqlite`,
TypeScript исполняется Node напрямую. Сервис, который годами крутится по cron, не должен падать
из-за пересборки нативного модуля.

Схема БД совместима с Postgres по структуре — миграция сводится к замене драйвера в `storage/db.ts`.

## Что дальше

По убыванию отдачи:

1. **Карточка дела в КАД** как ещё один провайдер обогащения: стадия дела, жалобы на торги.
   Открытого API нет и защита от роботов серьёзная, поэтому пока честнее ручные факты.
2. **LLM поверх остатка.** Детерминированные правила покрывают типовые формулировки; языковая
   модель имеет смысл на том, что они не разобрали, — и результат нужно складывать в те же поля,
   чтобы оставалась воспроизводимость.
3. **Чек-лист подачи**: комплект документов, расчёт задатка, напоминания по дедлайнам.
4. **Учёт сделок**: воронка от интереса до перепродажи, чтобы ликвидность считалась по факту,
   а не по экспертной таблице.
5. **Замена экспертной таблицы ликвидности** в `src/score/liquidity.ts` на статистику из
   накопленных сделок: медианный срок от покупки до перепродажи по своим же операциям.

Чего здесь сознательно нет — подачи заявок и автоматических ценовых предложений. Причины
в [docs/strategy.md](docs/strategy.md): ключ УКЭП нельзя передавать сервису, а роботы-снайперы
дешевле арендовать готовыми, чем писать и сопровождать.

## Воронка сделок

Скоринг отвечает «стоит ли смотреть», сделка — «что сделать сегодня и к какому сроку».

```bash
radar deal add cad:77:06:0004009:1234 --buyer company --max 6000000
radar deal show cad:77:06:0004009:1234    # вехи и пакет документов
radar deal move cad:77:06:0004009:1234 checking
radar deal done cad:77:06:0004009:1234 documents
radar remind                               # напомнить о приближающихся сроках
```

**Сроки считаются назад от окончания приёма заявок** — единственной даты, заданной извне.
И считаются в **рабочих** днях: банковский перевод задатка не идёт в выходные, а заявка,
поданная в пятницу с задатком «в пути», к понедельнику превращается в недопуск.

```
приём заявок до среды 02.09
        подать заявку   ←  1 раб. дн.  →  вт 01.09
    перечислить задаток ←  3 раб. дн.  →  пт 28.08   (не вс 30.08)
     собрать документы  ←  3 раб. дн.  →  вт 25.08
```

Производственный календарь в код не зашит: переносы праздников меняются ежегодно,
а устаревший зашитый календарь опаснее отсутствующего — он выглядит точным. Праздники
задаются в `HOLIDAYS`, по умолчанию учитываются только выходные.

Вехи, посчитанные в рабочих днях, показываются **без времени**: срок известен с точностью
до дня, и выдавать «до 28 августа» за «до 03:00 28 августа» нечестно. Время показывается
только у торговой сессии — оно взято из извещения.

**Пакет документов** зависит от типа покупателя и вида имущества. Смысл не в перечислении
очевидного, а в том, чтобы поймать пункты с длинным сроком получения: нотариальное согласие
супруга и решение об одобрении крупной сделки не делаются в день подачи — именно на них
срываются сроки. Такие пункты помечены и выносятся в напоминание отдельно.

Список типовой. Последний пункт каждого чек-листа — сверить состав с сообщением о торгах:
организатор вправе установить свою форму заявки и дополнительные требования.

**Машина состояний** не пускает назад и не даёт пропускать шаги. «Задаток перечислен» после
«заявка подана» означает, что что-то пошло не так, и это надо заметить сразу:

```
$ radar deal move <lot> won
Переход «interest» → «won» не предусмотрен. Из «интерес» возможно: проверка, отказались
```

Сумма задатка берётся из извещения и **не вычисляется**: ошибка здесь означает недопуск,
поэтому при её отсутствии напоминание честно говорит «в извещении не указан».

## Что именно не разбирается

Три ошибки разбора площади нашлись только потому, что кто-то вручную прогнал шесть строк
из настоящих извещений. Так искать баги нельзя: правило молча перестаёт срабатывать,
лот теряет площадь или график снижения, и заметно это лишь по тому, что он не всплыл в топе.

```
$ radar doctor

Полнота извлечения по 5 лотам

████████████░░░░░░░░  60%  ИНН должника извлечён (3/5)
████████████████░░░░  80%  Есть устойчивый идентификатор (4/5)
████████████████████ 100%  График снижения разобран (2/2)

Требуют внимания:

ИНН должника извлечён — 60%
  без него хуже работает дедупликация лотов без кадастрового номера и VIN
  · Автомобиль TOYOTA CAMRY, 2019 года выпуска
```

Метрика считается только по применимым лотам: спрашивать площадь с автомобиля незачем,
и он не должен портить долю. Где применимых нет, показывается «н/д», а не 100% —
это разные вещи.

Ниже порога метрика попадает только при осмысленной выборке (по умолчанию от 10 лотов):
на трёх лотах любая доля — шум. Если метрика ниже порога, но выборка мала, отчёт скажет
об этом прямо, а не промолчит — «всё хорошо» и «судить рано» путать нельзя.

Порядок работы замкнутый: покрытие → примеры → правило в `src/normalize/text.ts` →
тест на настоящем тексте → повторный `doctor`. Пока покрытие не измерено, подключать
языковую модель к разбору незачем: неизвестно, какой остаток она должна закрыть.

## Насколько оценка вообще работает

`doctor` меряет, что сервис сумел извлечь. `backtest` проверяет другое и более важное:
предсказывает ли оценка цену, за которую лот реально ушёл. Без этого дисконт в скоринге —
число, полученное делением на неизвестно что.

```
$ radar backtest

Проверено 4 из 25 продаж (пропущено 21: на дату сделки ещё не набралось аналогов)

Медианная ошибка оценки: 3.9%
Смещение: -3.0% (систематически занижаем)

Множитель не предлагается: выборки мало либо смещение в пределах шума.
ESTIMATE_UPLIFT остаётся равным 1 — это осознанная позиция, а не недоделка.
```

Две методические оговорки, без которых проверка была бы самообманом:

- **Проверяемая продажа исключается из выборки.** Если оценивать сделку, включив её саму
  в число аналогов, оценка подгонится под ответ — и тем сильнее, чем меньше выборка.
- **Заглядывать в будущее нельзя.** Учитываются только сделки, состоявшиеся раньше
  проверяемой: более поздних в тот день ещё не существовало, и оценка на их основе
  была недоступна. Отсюда большая доля пропущенных на малой истории — это не сбой,
  а признак того, что проверка честная.

Самый практичный результат — **измеренное смещение**. Оно превращает `ESTIMATE_UPLIFT`
из догадки в число с основанием. Множитель предлагается только при выборке от 30 сделок
и смещении выше 5%: подкручивать оценку по десятку сделок — это подгонка под шум,
ровно то, из-за чего множитель по умолчанию равен единице.

Чего проверка **не** подтверждает: риск-флаги и веса скоринга. В истории продаж нет текста
извещения, поэтому проверяется только оценка стоимости.

## Сопровождение

Сервис зависит от внешнего мира в трёх местах, и все три устаревают: спецификация API
ЕФРСБ, схема ответа ГИС Торги и порядок продажи имущества по 127-ФЗ. Для регулярной
сверки есть готовый протокол — [docs/prompts/audit-and-update.md](docs/prompts/audit-and-update.md).
Прогонять раз в квартал и после каждого заметного изменения в законодательстве.

Протокол устроен так, чтобы нельзя было отчитаться об успехе, ничего не проверив:
каждое утверждение требует ссылки, каждое изменение — теста, а всё, что подтвердить
не удалось, обязано остаться непроверенным и явно помеченным, а не тихо «исправленным».

## Вынести в отдельный репозиторий

Проект самодостаточен и не связан с кодом вокруг. Перенос с сохранением истории:

```bash
git subtree split --prefix=bankrot-radar -b bankrot-radar-only
git push git@github.com:<owner>/bankrot-radar.git bankrot-radar-only:main
```

Либо просто скопировать каталог — внешних ссылок за его пределы нет.
